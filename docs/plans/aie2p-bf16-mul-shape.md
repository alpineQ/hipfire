# AIE-2P bf16 mul-and-store: hardware shape characterization

This doc captures the empirically-determined behavior of AIE-2P's
bf16 multiply + bf16 store pipeline, as observed on hipx (Strix
Halo NPU2). It explains why bit-for-bit equivalence between a
naive CPU model and the NPU output is not achievable without an
empirical lookup table, and what acceptance criteria the
`hipx-verify-asym3-dequant` binary uses instead.

## What is bit-faithful

The mul `aie::mul(bfloat16, bfloat16) -> accfloat` is **bit-faithful**
when the accumulator is read out as f32. Verified via the
`asym3_dequant_256_f32` diagnostic kernel
(`kernels/aie2p/asym3_dequant_256_f32/`) and a sweep across 14336
(cnorm bf16, cb_idx) pairs in `bench/asym3_mul_sweep.tsv`. The
ratio between CPU-fp32-faithful product and NPU f32 accumulator is
exactly 1.0000000000 across every pair. Both bf16 inputs are
promoted to f32 (lossless on bf16 inputs since bf16 has 8-bit
mantissa and fp32 has 24-bit mantissa) and multiplied in fp32.

## What is NOT bit-faithful

The down-conversion `accum::to_vector<bfloat16>()` does not
correspond to any standard rounding mode (RNE / RTZ / RAZ /
round-half-up). Three independent tests with bf16-EXACT cnorm
(eliminating cnorm conversion as a variable, isolating the
down-conversion step):

```
Case A: cnorm 0x3EC8 (0.39), cb 0x3E0A. f32 product = 0x3D57A000
        RAZ predicts 0x3D58, NPU produces 0x3D56  (-2 ULP)

Case B: cnorm 0xBFF5 (-1.91), cb 0x3D3E. f32 product = 0xBDB5D600
        RAZ predicts 0xBDB6, NPU produces 0xBDB7  (+1 ULP)

Case C: cnorm 0xBF70 (-0.94), cb 0x3DAB. f32 product = 0xBDA05000
        RAZ predicts 0xBDA1, NPU produces 0xBDA1  (match)
```

Mixed directions. No single closed-form rounding rule fits all
three. The bf16 down-conversion's behavior depends on bits beyond
what a simple rounding mode captures. AMD does not publish the
exact AIE-2P fp32 to bf16 hardware rounding semantics. Plausible
explanations:

1. The hardware instruction is a fused `cvtf32_to_bf16` with a
   non-IEEE rounding (saturating, magnitude-aware bias, or some
   stochastic/dither component).
2. `to_vector<bfloat16>` for the bf16 path uses a wider-than-fp32
   internal accumulator that `to_vector<float>` truncates to
   IEEE fp32 with standard RNE. (Possible but not proven; the
   sweep showed `to_vector<float>` is bit-faithful w.r.t. CPU
   fp32 product on bf16 inputs, which would require accfloat to
   already be at fp32 precision.)

Empirically, the deviation from RAZ is bounded at <= 2 ULP. We
have not observed a deviation > 2 ULP across any test.

## What is NOT yet characterized

The kernel's `(bfloat16)(*float_ptr)` cast for cnorm input. We
observed that the cast has its own rounding mode, distinct from
RNE. RTZ and RAZ both fit some cases but not all. Treating the
cnorm cast and the output down-conversion as a coupled system
empirically caps deviations at 2 ULP, but the input cast hasn't
been characterized as cleanly as the output.

## Implications for stage 1.1 (correctness verifier)

The original contract called for "bit-for-bit match against the
iGPU reference." Two interpretations:

(a) Naive: CPU computes a fictional ideal bf16 mul (using IEEE
    rounding rules), compare to NPU bf16 output bit-by-bit. This
    interpretation is **not achievable** without exhaustive
    empirical characterization, because IEEE rounding rules do
    not describe AIE-2P hardware.

(b) Hardware-shape: CPU emulates AIE-2P bf16 hardware exactly,
    compare bit-for-bit. This is achievable via a
    `(cnorm_bf16, cb_idx) -> bf16_output` LUT generated by an
    empirical sweep of all bf16 cnorm values x 8 codebook entries
    (524k entries, 1 MB blob). The verifier becomes a lookup +
    bit comparison. Bit-exact by construction.

Stage 1.1 currently uses a third path:

(c) Bounded-shape: CPU uses our best closed-form approximation
    (RTZ for cnorm, RAZ for output). Verifier enforces three
    gates that catch real bug classes without depending on a
    fictional hardware model:

    1. **Determinism**: same input twice -> same output.
    2. **Max bf16 ULP per element <= 3** across 100+ random seeds
       (1 ULP of headroom over the empirical max of 2). Catches
       structural bugs (codebook precision, layout, unpack,
       off-by-one) which produce errors much larger than the
       few-ULP hardware rounding floor; the headroom guards
       against single-measurement noise tripping the gate.
    3. **|mean signed ULP error| <= 0.5** across all diff'd
       elements (~10x headroom over the empirical ~0.05). Catches
       large-magnitude systematic-bias bugs.

    Empirical envelope post-codex codebook RNE fix (commit 5adfd07):

    ```
    100 random seeds, verify_asym3_dequant.rs:
      determinism:    PASS
      max ULP:        2
      mean signed:    -0.06 (codebook RNE matches kernel)

    1000 random seeds, verify_asym3_dequant_layer.rs (N_ITERS=1024):
      determinism:    PASS across all 1000 seeds
      max ULP:        2
      mean signed:    +0.0088

    1024 dispatches, hipfire_x_asym3_shadow.rs (16 layers x 8 heads
    x 8 positions, realistic varied cnorm):
      determinism:    PASS
      max ULP:        2
      mean signed:    -0.02 (per-layer max bias +0.24)
    ```

    The codex review caught that the kernel codebook is `bfloat16(
    f32_lit)` RNE-rounded, not RTZ-truncated. Earlier CPU models
    used RTZ for codebook conversion which produced +0.70 mean
    bias by mismatching idx in {1, 3, 4, 6} where dropped bits
    >= 0x8000. After fixing the CPU model to use RNE for codebook
    (kernel matches RNE), the mean drift collapsed to under 0.1.
    The bounded ULP residual reflects the AIE-2P bf16 mul-and-
    store hardware shape (-2 / +1 / 0 ULP cases documented above).

    Strict bit-for-bit mode is preserved as `ASYM3_STRICT=1` for
    future use when a LUT lands.

## Why option (c) instead of (b)

Option (b) is more thorough but locks the verifier to one specific
kernel revision. Any change to the kernel (different MLIR-AIE
build, different Peano version, different aiecc revision, etc.)
invalidates the LUT and requires regeneration. Option (c) catches
the same bug classes (codebook, layout, unpack, off-by-one) without
that brittleness, and shipping today is more valuable than a
LUT-locked verifier.

When stage 1.3 ships (engine integration with shadow-mode
comparison against the iGPU asym3 path on real prompts), the
production correctness check is far stronger than any standalone
verifier. If shadow mode ever shows a quality regression, we can
revisit option (b) with a known-bad scenario to debug against.

## When to revisit option (b)

- shadow mode at stage 1.3 shows a quality regression that the
  bounded-shape verifier missed
- a kernel revision introduces a >2-ULP deviation that should
  not be silently accepted
- AMD publishes the AIE-2P bf16 rounding semantics (then we'd
  reconsider option (a) with the documented rules)
