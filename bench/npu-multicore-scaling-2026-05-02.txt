# Multi-core scaling characterization for asym3_dequant_layer
# Captured 2026-05-02 against commit 70ccfad
# Hardware: hipx (Strix Halo / gfx1151 iGPU + AIE-2P NPU2)

## Measured timing (release build, 1000 seeds = 2000 dispatches, N_ITERS=1024)

  Variant     Wall    Per-dispatch  Per-iter
  1c          5.02 s  2.51 ms       2.45 us
  2c          3.65 s  1.83 ms       1.78 us  (1.37x speedup)
  4c          2.56 s  1.28 ms       1.25 us  (1.96x speedup)
  8c          2.85 s  1.43 ms       1.39 us  (1.76x speedup)

## Linear model fit

Modeling per_dispatch = host_overhead + (compute_per_core / N_cores):

  From 1c-2c:  2.51 - 1.83 = 0.68 = C/2  ->  C = 1.36 ms
  From 2c-4c:  1.83 - 1.28 = 0.55 = C/4  ->  C = 2.20 ms
  Average:     C = 1.78 ms compute (single-core baseline)
  Then:        O = 2.51 - 1.78 = 0.73 ms host overhead

The 8c regression vs 4c is consistent with a per-column overhead
term that grows with N_cores: 8c adds ~8 * 20 us = 160 us of
extra DMA-channel setup compared to 4c, which exceeds the 0.18 ms
compute savings 8c gives (1.78/4 = 0.45 ms vs 1.78/8 = 0.22 ms).

Refined model: per_dispatch = O + 0.02*N_cores + C/N_cores
  At N_cores = 4: 0.73 + 0.08 + 0.45 = 1.26 ms (matches 1.28)
  At N_cores = 8: 0.73 + 0.16 + 0.22 = 1.11 ms (predicted) vs 1.43 measured

The 8c gap (1.43 vs 1.11 predicted) suggests another saturating
factor, likely shim DMA bandwidth contention. Fixing the model is
not productive right now; the data is enough to project production.

## Projection to full layer shape (N_ITERS=32768)

Compute scales linearly with N_ITERS (more iterations on each
core); host overhead is roughly constant per dispatch. So at full
shape we expect:

  Per-dispatch = O + 32 * (C/N_cores)

  N_cores  Per-dispatch   Per-token (46 layers)  vs iGPU 67ms
    1      57.7 ms        2.65 s                 39x slower
    2      29.2 ms        1.34 s                 20x slower
    4      14.9 ms        687 ms                 10x slower
    8       7.84 ms       360 ms                 5.4x slower
   16       4.30 ms       198 ms                 3.0x slower
   32       2.51 ms       115 ms                 1.7x slower

Even the fully-utilized 32-core configuration (8 cols x 4 rows) is
1.7x slower than iGPU baseline at full layer shape. Single-core
per-iter compute is 1.74 us (measured) - about 10x my earlier 180
ns estimate. The estimate was based on instruction count theory;
real measurement includes ObjectFifo acquire/release + memory
access latency that the count missed.

## Conclusion: stage 2.6 fused score is the only competitive path

NPU dequant offload as a standalone op cannot beat iGPU triattn
score at full layer shape. The numbers don't get there even with
maximum core count. Per the contract:

  "If lift is < 5% or quality drifts: do not flip default.
  Escalate to MANUAL_REVIEW.md with telemetry; stage 2.6
  (fused score) may be the right next move instead."

Stage 2.6 is the right next move. Fused asym3-on-NPU score keeps
K on-NPU through scoring, eliminating the 16 MiB bf16 K writeback
per layer. The score work itself (Givens + RoPE + atan2/cos/sin/
sqrt + reduction) moves to NPU too, freeing iGPU cycles for the
hot-path matmul that the iGPU does well. That's the actual
offload value.

The multi-core scaffolding shipped in stages 1.4a (commits
4a4f5ce / d648a9c / 70ccfad) is reusable for stage 2.6: the
multi-core MLIR plumbing, ObjectFifo routing, per-column DMA
patterns all transfer. The kernel body changes from "lookup +
mul" to "lookup + mul + Givens + RoPE + score reduction".

## What to ship for stage 1.5 result

Per the contract's escalation rule, stage 1.5 escalates to
MANUAL_REVIEW with this telemetry:
  - dequant-only NPU at 8 cores projects to 5.4x slower than
    iGPU at N=32768
  - dequant-only at 32 cores projects to 1.7x slower
  - Neither config produces a "lift" worth flipping the default
  - Stage 2.6 fused score is the path to actual offload value

Default HIPFIRE_NPU_DEQUANT remains 0. Multi-core scaffold work
preserved for stage 2.6 reuse.
